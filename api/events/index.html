    Realtime events¶

    Firebird can tell its clients that something happened: a trigger or procedure runs POST_EVENT 'order_placed', and when its transaction commits every attachment listening for that name is notified. FirebirdREST forwards these notifications to HTTP clients as Server-Sent Events, so a page or a service can react to a change without polling. PostgREST has no equivalent; Supabase provides it through a separate service.

    Exposing events¶

    Events carry no data and Firebird checks no privilege before delivering them, so FirebirdREST only streams the names you list:

    db-events = "order_placed, stock_changed"
db-events-roles = "web_user"       # optional: only these roles may listen

    Without db-events the endpoint is off (404, FBRST135). Without db-events-roles any authenticated role may listen; the anonymous role may listen only when it is listed. As for any request, the role must be granted to the authenticator user.

    In the database, post the event where the change happens:

    CREATE TRIGGER orders_posted AFTER INSERT ON orders
AS
BEGIN
  POST_EVENT 'order_placed';
END

    The example database posts order_placed from the place_order procedure and has a notify(name) procedure that posts any event, for trying things out.

    Listening¶

    curl -N 'localhost:3000/events/order_placed,stock_changed' -H "Authorization: Bearer $JWT"

    retry: 3000
: listening order_placed,stock_changed

: keepalive

id: 1
event: order_placed
data: {"name":"order_placed","count":1}
    • The path names one event or several, comma separated. Names are matched as Firebird stores them: stock_changed and STOCK_CHANGED are the same event.
    • Every notification is one SSE message: event is the name, data repeats it with count, the number of posts Firebird merged into this notification (one transaction posting the same event ten times is delivered once, with count: 10), and id identifies the notification for reconnecting.
    • A comment line (: keepalive) is sent every 15 seconds so proxies and clients keep the connection open. retry: 3000 tells EventSource clients to reconnect after 3 seconds.
    • The stream is not subject to server-request-timeout; it ends when the client closes it or the server shuts down (then with event: error and data: {"message":"server shutting down"}).
    • An event that isn't exposed is 404 (FBRST136); a role that may not listen gets 403 (FBRST137, 401 when anonymous).

    A client hears that something changed, not what: it then reads the data it needs through the API, under its own role and grants. That keeps events safe to expose to many roles: an event name is the only thing they learn.

    Browsers' EventSource can't send an Authorization header. Use fetch with a streaming body instead, as firebirdrest-js does, or put the token in a cookie that a proxy turns into the header.

    How it works¶

    One Firebird attachment listens for all exposed events and fans the notifications out to the HTTP streams in process: a thousand listeners cost the database one connection. If the connection to the database is lost the server resubscribes every 30 seconds; streams opened meanwhile get event: error with "not listening" and should reconnect. A stream that isn't read fast enough loses notifications rather than slowing the others, and is sent a reset.

    With several FirebirdREST instances each listens by itself, so a client connected to any of them hears every event.

    Reconnecting without missing notifications¶

    A notification's id is <server>-<number>. A client that reconnects sends the last one it saw in a Last-Event-ID header (EventSource does this by itself, and so does firebirdrest-js), and the stream starts with the notifications it missed, for the events it names, before the live ones. The server keeps the last 1,000 notifications for this.

    When it can't know what was missed, the stream says so instead of carrying on as if nothing happened. It sends a reset, first thing on reconnect or at once on an open stream:

    event: reset
data: {"reason":"the server restarted, or this is another instance; notifications may have been missed"}
    Reason When
    the server restarted, or this is another instance the id comes from another server process: a restart, or a load balancer sending the reconnect to another instance
    more notifications were posted than the server keeps the client was away for more than the last 1,000 notifications
    the server lost its connection to the database events posted while nobody listened are gone; sent to open streams when the server listens again, and to ids from before
    notifications were dropped the stream wasn't read fast enough
    unknown Last-Event-ID the id isn't one this server issued

    On a reset, reload what the page or service shows from the API, as on a first start. error and reset are the stream's own message types, so they can't be used as event names in db-events.

    Surviving restarts: a change log¶

    The replay buffer lives in one server process. For a client that must see every change across restarts, deploys and several instances, record the changes in the database and use events only as the signal to look:

    CREATE TABLE changes (
  id         BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  entity     VARCHAR(30) NOT NULL,
  entity_id  INTEGER NOT NULL,
  op         CHAR(1) NOT NULL,                 -- I, U or D
  changed_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP NOT NULL
);
CREATE INDEX changes_at ON changes (changed_at);

SET TERM ^ ;
CREATE TRIGGER orders_changes FOR orders AFTER INSERT OR UPDATE OR DELETE
AS
BEGIN
  INSERT INTO changes (entity, entity_id, op)
  VALUES ('orders', COALESCE(NEW.id, OLD.id),
          CASE WHEN INSERTING THEN 'I' WHEN UPDATING THEN 'U' ELSE 'D' END);
  POST_EVENT 'orders_changed';
END^
SET TERM ; ^

GRANT SELECT ON changes TO ROLE web_user;

    The client keeps the time of its last read, durably, and on every orders_changed notification or reset, and when it starts, asks for what changed since:

    curl 'localhost:3000/changes?changed_at=gte.2026-10-31T10:15:00&order=id' -H "Authorization: Bearer $JWT"

    Read with some overlap, for example from a minute before the last read, and skip ids already applied. id and changed_at are set when a row is inserted, not when its transaction commits, so a slow transaction can commit a change older than one the client has already read; the overlap must be longer than the longest transaction that writes these tables. Delete old rows from changes on a schedule.

    With firebirdrest-js¶

    const channel = client.channel('order_placed', 'stock_changed')
  .on('order_placed', (e) => refreshOrders())      // e.name, e.count
  .on('*', (e) => console.log('event', e.name))
  .onReset((reason) => reloadEverything())         // notifications may have been missed
  .subscribe((status) => console.log(status))     // "open", "closed", "error"
// later
channel.unsubscribe()

    The channel reconnects by itself with a growing delay while the server is unreachable, and sends the last id it saw, so missed notifications are replayed or onReset is called.

    Metrics¶

    With db-events set, /metrics reports open streams, notifications received by event, notifications delivered, resets sent, and times the database subscription was lost (monitoring).
