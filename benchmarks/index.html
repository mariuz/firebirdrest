    Benchmarks¶

    FirebirdREST ships a load tool in bench/ so you can measure it against your own hardware and data.

    Running it¶

    # 1. a database with the example schema
isql -user SYSDBA -password masterkey -i examples/bookstore.sql localhost:/data/bench.fdb

# 2. ~400k rows: 2,000 authors, 100,000 books, 200,000 book/tag links,
#    5,000 customers, 50,000 orders with 100,000 items (takes a few seconds)
go run ./bench seed -dsn SYSDBA:masterkey@localhost:3050/data/bench.fdb

# 3. start FirebirdREST against it, then
go run ./bench run -url http://localhost:3000 -c 16 -d 10s -token "$JWT_FOR_WEB_USER"

    run prints a Markdown table with requests per second and p50/p95/p99 latency for each scenario. -only <text> runs the matching scenarios only. Scenarios marked "rollback" send Prefer: tx=rollback, so the database is unchanged afterwards.

    Measure on a quiet machine

    The client, FirebirdREST and Firebird all compete for CPU. With Docker, connect to the container's IP rather than a published port: Docker's userland port proxy cost about 30% of throughput in our runs.

    Regression checks in CI¶

    The Performance workflow benchmarks every change to the server against the latest release, on the same runner and the same seeded Firebird 5 database, and fails when a scenario got more than 15% slower. It runs on pushes to main and pull requests that touch the code, weekly, and on demand (with another release or threshold). The report is the run's summary page:

    | Scenario | v0.7.0 req/s | 1a2b3c4 req/s | change | range of rounds |   |
| row by primary key | 2212 | 1854 | -17.9% | -19% to -9% | **slower** |
| insert 1 row (rollback) | 827 | 881 | +3.4% | +0% to +11% |  |

    A shared CI runner's speed drifts from minute to minute, so a single measurement of each version can't be trusted. bench compare measures both servers in alternation, scenario by scenario, for five rounds, swapping which goes first each round; each round gives a ratio taken seconds apart, and a scenario's verdict is the median of its five ratios. A slow round, or a slowdown that hits both servers, doesn't fail it.

    Checked before relying on it, on a 4-CPU machine:

    • The same build on both sides (an A/A test): single rounds differed by up to 16%, the medians by at most 7.3%. No scenario failed.
    • A build with 1 ms added to every read: reading a row by key came out 17.9% slower and failed the run; inserts, and reads where 1 ms is a smaller share of the time, passed.

    So the check catches a change that costs a fast request about a millisecond, and ignores the runner's noise. Run it locally against any two servers on one database:

    go run ./bench compare -baseline http://localhost:3001 -candidate http://localhost:3000 \
  -secret "$JWT_SECRET" -rounds 5 -d 3s

    The current code compared with the code before the performance work (commit 712a7fb), on a 4-vCPU Intel Xeon 2.1 GHz VM with 16 GB RAM, Firebird 5.0.4 in Docker on the same machine, 16 concurrent clients, pool of 32 connections. The two versions ran side by side and each scenario alternated between them (median of two 4-second runs) so that drift in the shared VM affects both equally. Absolute numbers depend heavily on hardware; compare the change column.

    Reading the numbers¶

    Requests that cost about the same in both engines (a row by key, a function call, a 25-row embed) land within 10% of each other: the HTTP and SQL-building layers of the two servers cost about the same, and the rest is the database. The differences come from how each server turns a request into SQL, and from the engines:

    • Embedding with paging (one-to-many, nested, 12–21× faster on FirebirdREST). PostgREST embeds in one statement with a lateral join per level, and PostgreSQL evaluates that join for every parent row the OFFSET skips: at offset=1900 the per-author aggregation runs 1,910 times for 10 result rows (178 ms in EXPLAIN ANALYZE; 560 ms for the three-level nest). FirebirdREST pages the parent rows first and fetches each level's children for those rows only, so the cost doesn't grow with the offset. Page 1 of the same request is fast on both; the advantage is in paging through embedded data, and in to-many embeds of parents with many children.
    • Bulk inserts (100 rows, 11× faster on PostgREST). PostgREST inserts the whole body in one statement (INSERT ... SELECT FROM json_populate_recordset). FirebirdREST used to run one INSERT per row, 100 round trips; since this measurement it sends the rows in EXECUTE BLOCKs (two for this body), which cut a single client's request from 20 ms to 6 ms. Under 16 concurrent clients the gain is only 127 → 191 req/s, because Firebird serializes concurrent inserts into the same table: the time spent in the database grows from 5 ms alone to 75 ms with 16 clients, for the old and the new code alike (a plain PSQL loop inserts 200,000 rows/s on this machine when nothing else writes). That ceiling is the engine's, and the benchmark, with every client inserting into one table, measures it. Single-row inserts are 2× slower than PostgREST's mainly through Firebird's commit cost.
    • Counting and aggregating 100,000 rows (count=exact, group by, 3× faster on PostgREST) and sorting 100,000 rows without an index (filter + order, 2×). These requests scan the whole table on both engines; PostgreSQL scans faster. FirebirdREST's count=planned/estimated avoid the scan when an estimate will do.
    • Pages of 100 rows and computed fields (0.7–0.8× at the time of this table). Counting the wire packets showed why: a read cost 7 round trips to Firebird, of which only two were the query (transaction start, the request context block plus the row-count request the driver added to it, execute, fetch, cursor close, commit). Since this measurement, reads reuse a read-only transaction per connection and the context block runs without the row-count request, which leaves 4 round trips. On the same machine and data, FirebirdREST went from 3,900 to 5,100 req/s on a row by key, 4,200 to 6,600 on the function call, 2,340 to 2,900 on the computed field (parity with PostgREST), 1,800 to 2,460 on the 25-row embed and 1,800 to 2,300 on the 100-row page (0.78× of PostgREST: the rest is the driver's per-row decoding). The next step is in the driver: sending the cursor close together with the following request, as fbclient does, would make it 3.

    The absolute numbers are for this machine; the ratios are what to take away. Firebird's engine is generally slower than PostgreSQL's at scanning and aggregating large tables, so an API that does mostly keyed reads, embeds and small writes compares well, and one that counts or groups large tables on every request does not, whichever REST layer is in front.

    What was optimized¶

    Profiling (admin-pprof = true) showed that time went into database round trips and Firebird compiling statements, not into Go code:

    1. Prepared statement cache. Firebird compiles every statement on prepare, which costs about as much as running a small query. FirebirdREST now keeps up to db-prepared-statements (default 256) compiled statements per role and reuses them across requests. A cache miss runs the query directly and prepares it in the background, so a busy pool can't deadlock.
    2. Request context only when used. Setting the request.* variables was a separate round trip on every request, taking 27% of CPU in the profile. At schema load FirebirdREST checks whether any view, trigger, procedure, function, package or default expression mentions request.. If none does, the step is skipped. When it is needed, all variables (and the db-pre-request procedure) go in one EXECUTE BLOCK.
    3. Faster JSON encoding. Responses are written by an encoder specialised for result rows (no reflection, 2 allocations for a 100-row page) instead of encoding/json, which was 25% of CPU on embed-heavy requests.
    4. Bulk inserts reuse one prepared INSERT for all rows with the same columns.

    Prepared statements and DDL¶

    Firebird keeps a lock on every table a prepared statement uses. ALTER TABLE and CREATE OR ALTER VIEW work while statements are cached, but DROP TABLE (or dropping a view, procedure, ...) waits until the statements using it are closed. Cached statements unused for db-prepared-statements-idle seconds (default 30) are closed automatically, and a schema reload closes all of them. Before dropping an object that is in active use, reload first:

    curl -X POST localhost:3001/reload     # admin server, or: kill -USR1 <pid>

    or turn the cache off with db-prepared-statements = 0.
